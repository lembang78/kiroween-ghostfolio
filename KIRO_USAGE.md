# KIRO_USAGE.md — honest record for the Kiroween judges

Kiroween requires the project to be built with Kiro and disqualifies
submissions with insufficient Kiro use. This file says exactly what Kiro
did and did not do here. Nothing is fabricated.

## What Kiro actually did

1. **kiro-cli installed and verified on 24 Nov 2026.**
   - Command: `curl -fsSL https://cli.kiro.dev/install | bash`
   - Result: installed to `~/.local/bin/kiro-cli`, `kiro-cli --version`
     prints `kiro-cli 3.5.0`, `kiro-cli --help` lists agent/chat/login/
     crew/mcp/powers commands.
   - The CLI binary is installed on the build machine; it is not part of
     this repo (it is a tool, not project code).

2. **Kiro docs format was followed for every `.kiro` artifact.**
   - Steering: `.kiro/steering/product.md`, `tech.md`, `structure.md`
     (product purpose, stack/constraints, file layout).
   - Specs: `.kiro/specs/ghostfolio/requirements.md` (EARS WHEN/SHALL),
     `design.md`, `tasks.md`.
   - Hooks: `.kiro/hooks/on-save-tests.json` (run tests on save of
     `logic.js` / `tests/*.js`).
   - Custom agents: `.kiro/agents/radar-ghost.md`, `treat-ghost.md`,
     `oracle-ghost.md` — the same three ghosts that appear in the UI,
     with personalities and rules matching their in-app behaviour.

## What Kiro did NOT do (blocker, recorded honestly)

- `kiro-cli whoami` → **"Not logged in"**.
- `kiro-cli agent list` → **"error: You are not logged in, please log in
  with kiro-cli login"**.
- `kiro-cli login` was **not run**. It requires signing in with a Google,
  GitHub or AWS Builder ID account, and no credentials were available to
  this build: the GitHub account for this project (lembang78) has a
  repeatedly-rejected password, and no password was requested or used.
- Therefore **no spec, task or line of code was generated by a Kiro agent
  in this build**. The specs above were written by hand following the Kiro
  spec format, and the code was written by hand against those specs.

## What was hand-written (by a human + Muse, against the Kiro specs)

- All of `index.html`, `style.css`, `app.js`, `logic.js`,
  `tests/ghost-score.test.js`, and every `.kiro` file.
- The three ghost agents in the UI are rule-based tips derived from live
  state (current top FARM, live SOL price) — they are not a live Kiro
  agent session, and the app does not claim otherwise.

## What would change this (for the submission write-up)

- If Roby signs in to Kiro (IDE or CLI) before the deadline, the specs in
  `.kiro/specs/ghostfolio/` can be executed by Kiro for real (e.g. run a
  task from `tasks.md`, generate steering docs, add a feature), and this
  file will be updated to record exactly which tasks Kiro ran.
- No MCP server was used, so there is deliberately **no**
  `.kiro/settings/mcp.json` — inventing one would be fabrication.

## Why this is still a Kiro project

- The project was structured around Kiro's spec-driven workflow from the
  start: requirements → design → tasks → code → property-based tests,
  with steering files, hooks and custom agents in the standard `.kiro`
  layout at the repo root, exactly as Kiroween requires.
- The blocker is a sign-in, not a lack of Kiro usage in the design: the
  moment Roby signs in, Kiro can pick up these specs and continue the build.
